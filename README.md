# **HormAS: A Framework for Generating Empathetic and Strategic Responses to Customer Reviews**

This repository contains the source code, data, and documentation for **HormAS (Hotel Review Management Assistant Service)**, a framework designed to generate nuanced and effective responses to customer reviews. HormAS leverages a multi-stage process involving sentiment, emotion, and intention analysis to craft replies that are not only contextually appropriate but also strategically aligned with reputation management goals.

The study is reported in the manuscript *"Designing a Generative Artificial Intelligence-Based Hotel Review Management Assistant: A Design Science Approach"*, included in this repository together with its revision documents (see Section 6.1).

***

## **1. System Architecture and Implementation**

This section provides a detailed overview of the HormAS framework, encompassing its frontend, backend, and database components. The entire system is designed based on the Design Science Research (DSR) methodology to ensure relevance and rigor.

### **Backend**
The backend is developed using **Python 3.10.2** with the **Django 5.0.1** framework to ensure stability and scalability. Its core responsibilities include:
* **NLP and Machine Learning:** Core logic for prompt processing and response generation is implemented using **LangChain 0.1.3**. This server leverages powerful Large Language Models like **OpenAI's GPT-4** and models from the **Hugging Face** ecosystem to perform analysis and generation tasks.
* **API Service:** **Django** application serves the processed outputs through a RESTful API, which is managed and exposed via **Nginx**. This server handles data aggregation and requests between the frontend and the machine learning components.

### **Frontend**
The frontend provides an interactive web interface for users. It was built with **Next.js 15.3.2 (React 19.0.0)** and served via **Node.js**. This interface allows users to:
* Input customer review texts.
* Initiate the analysis and generation process.
* Compare responses generated by the HormAS framework against those from general-purpose language models.

### **Database and Infrastructure**
* **Database:** The system employs **Amazon RDS (PostgreSQL 15)** to store user inputs, the extracted analytical data (sentiment, emotion, intention), and the final generated responses for evaluation and further analysis. A backup mechanism to AWS is in place for data integrity.
* **Infrastructure:** The entire framework is containerized using **Docker** and orchestrated with **Kubernetes**, allowing for scalable deployment and robust management of the microservices architecture.

The deployable implementation lives under [`service/`](service/) (Django backend, Next.js frontend, Docker Compose samples); the model-side modules (embedding utilities, LLM tooling, prompt templates) live under [`model/`](model/).

## **2. Core Methodologies: Prompt Engineering**

HormAS utilizes a sophisticated generating framework that first deconstructs user input and then synthesizes that analysis into a final response. This process is orchestrated through advanced prompt engineering techniques: **Chain-of-Thought (CoT)**, **Zero-shot CoT**, and **Function Calling**. The production prompt templates are implemented in [`model/tool/prompt.py`](model/tool/prompt.py).

#### **2.1. Chain-of-Thought (CoT) Prompting**

**Concept**
CoT is a technique that guides an LLM to solve complex problems step-by-step by providing examples that include the **reasoning process or chain of thought** leading to the answer, rather than just the final answer itself. For creative or analytical tasks, CoT can also be used by **instructing the model to follow a specific reasoning framework** before producing the final output.

**Key Paper**
* **Title:** [Chain-of-Thought Prompting Elicits Reasoning in Large Language Models](https://arxiv.org/abs/2201.11903)
* **Authors:** Jason Wei, Xuezhi Wang, Dale Schuurmans, et al. (2022)

**✅ CoT Prompt Template (response generation)**

```
You are an expert Marketing Manager specializing in online reputation management. Your task is to craft a thoughtful and effective response to a customer review.

To ensure the highest quality response, you must follow this step-by-step reasoning process before writing the final reply.

## Step-by-Step Analysis ##

Step 1: Analyze Customer Sentiment.

Based on the provided 'Customer Sentiment', briefly explain how the overall tone of your response (e.g., apologetic, grateful, neutral) should be shaped.

Step 2: Analyze Customer Emotion.

Based on the 'Customer Emotion', identify the core feeling the customer is expressing (e.g., frustration, delight, disappointment). How will you validate this specific emotion in your response?

Step 3: Analyze Customer Intention.

Based on the 'Customer Intention', determine what the customer hopes to achieve with their review (e.g., receive a solution, warn others, praise the service). What specific action or information must your response contain to address this intention?

Step 4: Synthesize and Formulate a Strategy.

Based on your analysis in steps 1-3, outline a brief strategy for the final response. Mention the key points you will include.

## Final Response Generation ##

After completing the analysis above, write the final, polished response to the customer. This response should directly reflect the insights from your step-by-step analysis.

Final Response to Customer:
[Your final, well-crafted response goes here]
```

#### **2.2. Zero-shot CoT Prompting**

**Concept**
Zero-shot CoT retains the power of CoT **without the need to provide any examples**. It works by appending a simple phrase, such as **"Let's think step by step,"** to the prompt, which guides the model to generate its own reasoning process before arriving at an answer.

**Key Paper**
* **Title:** [Large Language Models are Zero-Shot Reasoners](https://arxiv.org/abs/2205.11916)
* **Authors:** Takeshi Kojima, Shixiang Shane Gu, Machel Reid, et al. (2022)

**✅ Zero-shot CoT Prompt (response generation)**
```
You are a professional Marketing Manager responsible for handling customer feedback. Your goal is to write a personalized and appropriate response to the following customer review, taking into account the provided analysis of their sentiment, emotion, and intention.

Carefully review all the information provided below.

Your final output should be only the direct response to the customer.

Let's think step by step.
```

#### **2.3. Function Calling for Structured Output**

**Concept**
Function Calling allows developers to obtain **structured data outputs** from the model. Instead of generating free-form text, the LLM is instructed to return a JSON object that "calls" a function defined by the user. This is the core mechanism used in the first stage of the HormAS framework to extract Sentiment, Emotion, and Intention.

#### ✅ Function Definition (Schema)
```json
[
    {
        "name": "Describer",
        "description": "Analyze the following 'Review'",
        "parameters": {
            "type": "object",
            "properties": {
                "User_Sentiment": {
                    "type": "string",
                    "enum": ["Positive", "Neutral", "Negative"],
                    "description": "Sentiment Analysis of the 'Review'"
                },
                "User_Emotion": {
                    "type": "string",
                    "enum": ["Anger", "Disgust", "Fear", "Happiness", "Contempt", "Sadness", "Surprise"],
                    "description": "Emotion Analysis of the 'Review'"
                },
                "User_Intention": {
                    "type": "string",
                    "description": "Intention Analysis of the 'Review'"
                }
            },
            "required": ["User_Sentiment", "User_Emotion", "User_Intention"]
        }
    }
]
```

#### ✅ Sample Prompt & Expected Output

**User Prompt to LLM:**
```
Please analyze the following customer review:

"I waited 30 minutes for a cold coffee. The barista was also very rude. I'm never coming back."
```

**Expected LLM Output (a JSON object that "calls" the function):**
```json
{
  "name": "Describer",
  "arguments": {
    "User_Sentiment": "Negative",
    "User_Emotion": "Anger",
    "User_Intention": "Complain"
  }
}
```

## **3. Model Configuration**

All language-model calls were made via the **OpenAI Chat Completions API**. The knowledge-extraction pipeline used **`gpt-3.5-turbo-0125`** and **`gpt-4-0613`**; the response-generation pipeline used **`gpt-4-0613`** exclusively (an exploratory comparison with GPT-4 Turbo was conducted but not retained in the final evaluation). Generation parameters were held constant across all calls:

| Parameter | Value |
| :--- | :--- |
| `temperature` | `0.0` |
| `max_tokens` | `512` |
| `top_p` | `1.0` |
| `frequency_penalty` | `0.0` |
| `presence_penalty` | `0.0` |

Each configuration was queried with a **single API call** — no best-of-N sampling, temperature sweeps, or manual selection — and **no post-processing, manual editing, or filtering** was applied to model outputs.

## **4. Data Collection and Evaluation Protocol**

This section documents the data underlying the empirical evaluation of HormAS and the protocols for the three measurement streams (knowledge extraction, response adoption, and stress reduction).

### **4.1. Source Corpus**

The source corpus was crawled from **TripAdvisor** and covers **696 hotels in the United States**. The raw collection contains **171,902 reviews**; after standard preprocessing (removal of missing values, deduplication), **137,760 reviews** remain. The corpus is heavily imbalanced toward positive feedback: 134,449 reviews (≈97%) carry 4 or 5 stars, 1,811 reviews carry 3 stars, and 1,502 reviews carry 1 or 2 stars.

The per-hotel raw files and the hotel-level metadata are stored under [`source/00_RAW/`](source/00_RAW/) and are never modified after collection.

### **4.2. Evaluation Samples**

From the corpus, a **150-review evaluation sample** was drawn — **30 reviews per rating level (1–5)**, uniformly at random from reviews with a posted manager response (the adoption evaluation's Human baseline requires one per review), excluding reviews of 30 characters or fewer.

* **Cost and accuracy experiments** use the **60 clearly polar reviews** from this sample (the 30 one-star and 30 five-star reviews), enabling a controlled comparison of prompt strategies between clearly negative and clearly positive conditions. This subset is materialized as [`source/01_SUBSET_60/subset_60_aligned.xlsx`](source/01_SUBSET_60/subset_60_aligned.xlsx).
* **The adoption-rate evaluation** uses the **full 150-review sample**.

Neutral (3-star) and mixed reviews are not part of the polar subset; performance on such review types was not quantitatively evaluated and is identified as a priority for follow-up work.

### **4.3. Category Scheme**

All annotation labels follow the categorical schemes adopted in the manuscript — Ekman (1971) for emotions and an eight-class scheme for intentions:

| Dimension | Categories |
| :--- | :--- |
| **Sentiment** | `Negative`, `Neutral`, `Positive` |
| **Emotion** *(Ekman 7)* | `Happiness`, `Sadness`, `Disgust`, `Fear`, `Surprise`, `Anger`, `Contempt` |
| **Intention** *(8)* | `Complaint`, `Experience Sharing`, `Praise`, `Recommendation`, `Feedback`, `Expression of Satisfaction`, `Expression of Dissatisfaction`, `Warning to Others` |

### **4.4. Knowledge Extraction Protocol (Manuscript Tables 4 and 5)**

Each combination of **model** (`gpt-3.5-turbo-0125`, `gpt-4-0613`) and **prompt strategy** (without-prompt, CoT, zero-shot CoT) is applied to all 60 polar reviews to extract sentiment, emotion, and intention, under the fixed generation parameters listed in Section 3.

To obtain cost and time estimates that do not depend on a single network draw, **each model × prompt combination is executed in three independent runs of the full 60-review sweep** (60 × 6 × 3 = 1,080 API calls). Reported cost and time values are means across the three run-level aggregates. Per-call logs (request metadata, token usage, latency, timestamps) and the run-level summaries are stored in [`source/A_api_rerun/`](source/A_api_rerun/).

Reference labels for the agreement comparison are produced by the **three researchers who conducted the study**, annotating all 60 reviews independently on each of the three dimensions. The **majority label** is the label assigned by at least two of the three labelers; items on which all three disagree are marked **ambiguous** and excluded from the agreement calculation. Inter-rater agreement is reported as **Fleiss' kappa with 95% bootstrap confidence intervals** (2,000 iterations), interpreted following Landis & Koch (1977). Raw labels and the IRR summary are stored in [`source/B_human_labelers/`](source/B_human_labelers/).

### **4.5. Response Adoption Protocol (Manuscript Table 7)**

**Approximately 30 evaluators holding relevant academic degrees** participate. Response sets are generated for the full 150-review sample, and each evaluator is presented with **10 reviews drawn evenly across the five rating levels** (two per level). For every review, the evaluator sees **four candidate responses**: (i) the actual hotel-manager reply posted on TripAdvisor for that review (the *Human* baseline) and (ii) three responses generated by GPT-4 using the basic, CoT, and zero-shot CoT prompts. Within each trial, the order of the four candidates is **randomized independently**, and the evaluator is **blind to the source** of each candidate. Each evaluator makes a single forced choice per review — selecting the response they would adopt as the official reply — yielding approximately **300 forced-choice trials**. Adoption rate is defined as the proportion of all trials in which a given response type was selected.

These evaluators are distinct from the three researchers who annotated sentiment, emotion, and intention (Section 4.4). Trial-level selection logs and the aggregate adoption-rate analysis — including the **Chi-square goodness-of-fit test against uniform selection** and **Bonferroni-corrected pairwise post-hoc tests** — are stored in [`source/C_adoption_evaluators/`](source/C_adoption_evaluators/).

### **4.6. Stress Experiment Protocol (Manuscript Section 4.5)**

The stress experiment is conducted with **nine researchers in the fields of hospitality and management**. Each participant completes two conditions in a fixed within-subject order — first responding to **ten negative reviews** (six mild-negative and four highly malicious) **without** artifact support, then responding to the same ten reviews **with** artifact support — recording a self-reported stress score on a 5-point Likert scale (1 = very low stress … 5 = very high stress) after each response. The fixed order is not counterbalanced; the resulting threats to internal validity (order, learning, fatigue, and expectation effects) are explicitly acknowledged as limitations.

Inference uses a **paired Wilcoxon signed-rank test** as the primary test (chosen for robustness to small n and the ordinal nature of single-item Likert data), a paired t-test as a sensitivity check, and **Cohen's d_z** as the effect-size estimator. Raw participant scores and the summary statistics are stored in [`source/D_stress_experiment/`](source/D_stress_experiment/); the survey instrument is under [`servey/`](servey/).

## **5. Empirical Results**

Results below mirror the revised manuscript (Tables 4–7 and Appendix Tables A1–A3); the underlying measurement and evaluation records live under [`source/`](source/).

### **5.1. Cost and Time of Knowledge Extraction (Table 4)**

| Model × Prompt | Cost (USD per 1,000 reviews) | Time Cost (% change from baseline) |
| :--- | :---: | :---: |
| GPT-3.5 *without prompt* (baseline) | `0.278` | `0.0` |
| GPT-3.5 *CoT* | `0.623` | `+20.0` |
| GPT-3.5 *zero-shot CoT* | `0.202` | `−65.9` |
| GPT-4 *without prompt* | `0.585` | `+4.5` |
| GPT-4 *CoT* | `15.146` | `+25.0` |
| GPT-4 *zero-shot CoT* | `4.650` | `−59.0` |

Values are means across three independent measurement runs. The baseline for time normalization is GPT-3.5 *without prompt*, fixed at 0% — Time Cost (%) = (mean latency of the model − mean latency of the baseline) / mean latency of the baseline × 100 — so `−65.9` indicates a 65.9% reduction in mean per-review latency relative to baseline.

The cost–time picture differs by model family. In the **GPT-3.5 family**, the zero-shot CoT prompt dominates on both axes: it is the cheapest configuration (0.202 USD per 1,000 reviews) *and* the fastest (−65.9%). In the **GPT-4 family**, the without-prompt baseline is cheapest (0.585) while zero-shot CoT carries a cost premium (4.650) in exchange for a substantial latency reduction (−59.0%) — a cost–time trade-off rather than dominance.

### **5.2. Cost and Time of Response Generation (Table 6, GPT-4 only)**

GPT-3.5 was excluded from response generation following a **pre-experimental pilot comparison on a 10-review subset**, in which GPT-3.5 and GPT-4 (zero-shot CoT) responses were compared on four dimensions — response coherence, contextual appropriateness, empathy in handling negative reviews, and risk of inappropriate or unsafe content. GPT-3.5 showed materially weaker performance on contextual appropriateness for highly negative reviews and produced a higher rate of generic, brand-uninformative replies; the pilot ratings are reported in **Appendix Table A1** of the manuscript.

| Prompt (GPT-4) | Cost (USD per 1,000 reviews) | Time Cost (% change from baseline) |
| :--- | :---: | :---: |
| *without prompt* (baseline) | `11.569` | `0.0` |
| *CoT* | `18.752` | `+16.8` |
| *zero-shot CoT* | `12.749` | `−42.4` |

A projection for a representative operational workload of 100 reviews, using zero-shot CoT in both stages, follows directly from the tables above:

```
Cost(100 reviews) = (4.650 + 12.749) USD per 1,000 reviews × 0.1
                  ≈ 1.74 USD
Time(100 reviews) = (per-review latency of extraction + per-review latency of generation) × 100
                  ≈ 9 minutes  (model time; excludes translation, server hosting,
                                production queueing overhead, and human review)
```

### **5.3. Knowledge Extraction Agreement with Human Labels (Table 5)**

Agreement is the proportion of reviews on which the model-predicted label matches the **human majority label**, separately per dimension.

| Model × Prompt | Sentiment | Emotion | Intention |
| :--- | :---: | :---: | :---: |
| GPT-3.5 *without prompt* | `100.00%` | `53.89%` | `32.22%` |
| GPT-3.5 *CoT* | `100.00%` | `68.33%` | `34.44%` |
| GPT-3.5 *zero-shot CoT* | `100.00%` | `66.11%` | `33.89%` |
| GPT-4 *without prompt* | `100.00%` | `67.22%` | `24.44%` |
| GPT-4 *CoT* | `100.00%` | `78.78%` | `36.67%` |
| GPT-4 *zero-shot CoT* | `100.00%` | `79.88%` | `35.00%` |

The 100% sentiment agreement reflects the **polar-only construction of the 60-review subset** (rating 1 + rating 5) and should not be read as a general performance claim; performance on neutral, mixed, or ambiguous reviews was not quantitatively evaluated. Class-level precision, recall, F1-scores, and confusion matrices for the strongest combination (GPT-4 zero-shot CoT) are reported in **Appendix Tables A2 and A3** of the manuscript.

**Inter-rater agreement** among the three labelers, with 95% bootstrap CIs:

| Dimension | Fleiss' κ | 95% CI |
| :--- | :---: | :---: |
| Sentiment | `0.82` | `[0.70, 0.92]` |
| Emotion | `0.52` | `[0.39, 0.64]` |
| Intention | `0.33` | `[0.22, 0.44]` |

Interpreted following Landis & Koch (1977). **Ambiguous items excluded** (no two-of-three majority): 0 of 60 for sentiment, 4 of 60 for emotion, and 15 of 60 for intention, yielding effective sample sizes of N = 60, 56, and 45 respectively. The downstream response-generation stage therefore relies principally on the sentiment and emotion signals; intention extraction remains the weakest dimension.

### **5.4. Response Adoption Rates (Table 7)**

| Response Method | Adoption Rate |
| :--- | :---: |
| Human (TripAdvisor manager reply) | `8.64%` |
| GPT-4 *without prompt* | `20.98%` |
| GPT-4 *CoT* | `19.34%` |
| GPT-4 *zero-shot CoT* | ***`51.02%`*** |

A Chi-square goodness-of-fit test against uniform selection rejects the null: **χ²(3) = 107.12, p < .001**. Bonferroni-corrected pairwise post-hoc tests indicate that the zero-shot CoT response was selected significantly more often than each of the other three candidates (all p < .001), while the difference between the *without-prompt* and *CoT* conditions was not significant.

Because the evaluator pool consists of degree-holding researchers rather than practising hotel managers, this finding is best interpreted as evidence from a controlled, blinded comparison rather than as a claim about operational hotel settings.

### **5.5. Stress Reduction (Manuscript Section 4.5)**

| Condition | M | SD | 95% CI | n |
| :--- | :---: | :---: | :---: | :---: |
| *without artifact* | `3.17` | `0.41` | `[2.85, 3.48]` | 9 |
| *with artifact* | `1.50` | `0.38` | `[1.21, 1.79]` | 9 |

Paired Wilcoxon signed-rank test: **W = 0.00, p = .004**. Paired t-test (sensitivity check): t(8) = 16.79, p < .001. Cohen's d_z = 5.6. The stress-reduction effect was most pronounced for highly malicious reviews.

Given the small sample (n = 9), the fixed condition order (without → with; not counterbalanced), and the use of a single-item self-reported Likert scale rather than a validated multi-item instrument, this finding should be interpreted as **preliminary evidence from a controlled within-subject study** rather than as a generalizable effect. A randomized, counterbalanced replication with practising hotel managers, larger n, and at least one validated instrument is identified as a priority for follow-up work.
